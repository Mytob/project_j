# Jellyfin Proxy v1.4 — Fail2ban and Security Management

## Scope

This document records the v1.4 requirements approved in the implementation
brief. v1.4 protects only VPS SSH authentication and administrator login. It
does not inspect Jellyfin user authentication and an SSH/admin ban must never
deny Jellyfin proxy traffic.

## Architecture

- `securityd` runs Fail2ban in the existing Compose stack. It uses only
  `NET_ADMIN`, read-only systemd journal and host machine-ID mounts, a
  read/write administrator event spool (needed to delete committed events and
  quarantine invalid ones), and private named volumes/sockets. The machine ID
  lets `journalctl` resolve the host journal directory. It is not privileged
  and has no Docker socket. The journal group and Caddy socket group are added
  only to this service.
- Fail2ban starts exactly two jails. `jp-ssh` reads genuine sshd journal
  records and applies exact IPv4/IPv6 addresses to a dedicated nftables SSH
  chain. `jp-admin` uses the authenticated backend's signed event spool and a
  no-op firewall action; administrator bans are enforced in Caddy so they
  cannot spill into Jellyfin traffic.
- The Go admin backend records successful and failed authentication with the
  resolved client IP. Forwarded addresses are trusted only from configured
  proxy CIDRs. HMAC-signed, immutable event files are fsynced before the login
  handler reports the event as stored. The controller processes them in
  timestamp order and deletes only events committed to persistent state.
  Successful logins reset pending failures but are not exposed in history.
- `internal/security` stores independent SSH/admin thresholds, pending
  failures, exact ban expiries, escalation history, processed event IDs,
  retained history and blocked-request aggregates in an atomic persistent
  state file. Defaults are three failures in ten minutes and progressive bans
  of 15 minutes, one hour, 24 hours and seven days; escalation resets after
  30 days without a new ban. History defaults to 30 days.
- Caddy's `jp_admin_bans` middleware keeps the live admin blocklist in memory
  and serves its control/status API only over a private Unix socket. A banned
  address receives HTTP 403 on the admin route; the access/Jellyfin route is
  unaffected. Controller reconciliation restores valid bans after restarts
  and never changes their saved expiry.
- `/security` uses the existing authenticated admin session, CSRF and SSE
  infrastructure. It contains health, configuration, filters, charts, active
  bans, unban actions and searchable retained events. The Overview security
  card is a compact summary linking to that page.

## Security and recovery boundaries

The security controller needs host networking so its single `NET_ADMIN`
capability can maintain the host SSH nftables chain. It also needs read access
to the systemd journal and Caddy's private security socket. No other service
receives these permissions. Its root filesystem is read-only, `/tmp` is a
bounded tmpfs, and persistent state is on named volumes. Admin and Caddy do
not receive the host journal or nftables capability.

If Fail2ban, event processing, journal access, nftables or Caddy synchronization
fails, the dashboard reports the specific degraded signal. The controller
retries recovery and leaves existing valid Caddy admin bans in place through
their original expiry. A failed Caddy sync does not indefinitely extend a ban.
The emergency recovery path for host lockout remains the VPS provider console.

Settings are validated before application. Active ban expiry timestamps and
escalation history are retained across policy changes. A failed apply restores
the prior policy. Manual unban clears the active ban and pending counter but
does not erase escalation history.

## Install, update and rollback

The security service and its pinned Fail2ban/systemd/nftables dependencies are
included in the self-contained release package. Use the normal package
installer/updater; persistent security state, event keys, active bans, and
admin configuration are separate from replaceable release files and must be
preserved. The package gate checks install, update, rollback and data
preservation with the security image included.

The Compose deployment derives `SYSTEMD_JOURNAL_GID` from the host's systemd
journal group. The host must provide `/run/log/journal` or `/var/log/journal`
read-only and permit `NET_ADMIN` in the security container. The integration
tests prove real nftables behavior inside an isolated Linux network namespace;
they do not by themselves prove host journald access, host-level SSH blocking,
full VPS reboot recovery, public TLS, or provider-firewall behavior.

## Required v1.4 gate

- Go unit tests and admin/SSE/CSRF regression tests.
- Desktop and mobile browser checks for the Security page, filters, unban,
  configuration and live updates.
- Isolated container tests for actual Fail2ban IPv4/IPv6 exact-IP enforcement,
  exact port/service scope, manual unban and unrelated nftables preservation.
- Caddy tests for admin-only 403, live ban/unban/expiry, blocked-request
  aggregation, private control socket and unaffected Jellyfin/streaming.
- Full-stack event integrity, failure/success reset, event replay/idempotence,
  container restart recovery, configuration rollback, UI unban and v1.3
  regressions.
- Self-contained package install/update/rollback with all seven images and
  existing persistent v1.3 data preserved.
- Actual isolated Ubuntu host checks for the real systemd journal mount,
  host-level SSH nftables blocking, SSH/admin service isolation and reboot
  recovery. This host gate must be recorded as blocked when no authorized host
  is available; Docker Desktop simulation is not a substitute.

### 1.4.1-dev VPS checks — 2026-10-18

The package at source revision `418d981f477a` was deployed to the authorized
Ubuntu test VPS. All six containers reported healthy after update and reboot.
The security container read genuine host sshd journal entries; Fail2ban
reported exactly the `jp-ssh` and `jp-admin` jails; reserved IPv4/IPv6 test
addresses were inserted into and removed from the live SSH nftables sets; and
the post-reboot chain contained one TCP/22 rule for each address family.
`jp-admin` uses its no-op firewall action. Normal DNS and TLS checks returned
200 for `darkcry.com`, 200 for `admin.darkcry.com`, and 403 for
`access.darkcry.com`, with certificate verification successful.

The 833 MiB host initially had no swap. A 2 GiB `/swapfile` is now active and
persistent through `/etc/fstab`, with `vm.swappiness=10`; it remained active
after the reboot. The first image import stalled before release activation;
the update succeeded after swap was added. Before reboot, duplicate identical
SSH nftables rule pairs were observed after service replacement. The reboot
cleared those duplicates; restart idempotence remains a follow-up to verify.

The operator subsequently confirmed that streaming works after this
deployment. A separate restart test reproduced duplicate SSH rules. The
Fail2ban startup action now checks for the shared table, chain, sets, and
address-family rules before adding them. The isolated regression test passed,
as did `build.ps1 test` and `build.ps1 release -Version 1.4.1-dev` on the
working tree. That preliminary package had a dirty source label and was not
deployed. The clean 1.4.2-dev release gate and version-matched VPS restart
retest are recorded below. The machine-readable full-release report was
generated before the live VPS evidence and still reports host checks blocked.
See `docs/TESTING.md` for package hash and commands.
